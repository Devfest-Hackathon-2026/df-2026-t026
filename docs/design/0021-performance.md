## 0. 一言で

遅いのはサーバーの処理ではない（温まっていれば1回 0.06〜0.16 秒）。待たされる所を、1回あたりの長さの順に並べるとこうなる。

| 待ち | 1回あたり | いつ起きるか |
|---|---|---|
| 記録すると、Gemini が返るまで入力欄ごと止まる | 5〜20 秒 | 記録のたび |
| 止まっていたサーバーの起動 | 2.6〜4.6 秒 | しばらくぶりの最初の操作 |
| 最初の読み込み | 約 6.7MB（うち 1.8MB は使っていないアイコンのフォント）。終わるまで画面は真っ白 | 初めて開いたとき・デプロイのあと |
| ノートを開くとスピナー、1行直すと保存を待って押し直し | 往復 1〜2 本。回線の良い PC で 0.1〜0.2 秒、スマホの回線ではその数倍（推測） | 操作のたび |
| 書いたあと、全部の画面が全部のノートを取り直す | 裏で数十本。待たされはしないが、回線とサーバーを取り合う | 何か書くたび。本番では、プリフライトを除いた通信の 94% がこの取り直し |

直し方は3つにまとまる。

- **読む**：アプリが状態を1か所に持ち、画面はそこからすぐ描く。取り直しは裏で1本だけ
- **書く**：先に画面へ出し、通信は後ろで順に送る。Gemini は利用者を待たせない所で呼び、呼ぶ回数は増やさない
- **最初の表示**：使っていない物を読ませず、サーバーをアプリの読み込みと同時に起こす

## 1. 測ったこと

### 1.1 通信の本数

| 場面 | 本数 | 確かめ方 |
|---|---|---|
| ログインした直後（ノート3冊、広い画面） | 3秒で 30 本（本体 15・プリフライト 15）。落ち着くまでに 36 本 | 確かめた。手元のリリースビルドを Chrome で開いて数えた。`GET /manuals` 3回、`GET /shared` 3回、3冊それぞれの `GET /manuals/:id` を2回ずつ |
| 本番の2日間（1,582 件） | プリフライト 593 件（37%）。残り 989 件のうち、取り直し（`GET /manuals`・`/manuals/:id`・`/me`・`/shared`・`/memos`）が 934 件（94%）、書き込みは 44 件 | 確かめた。Cloud Run のリクエストログ。書き込み1回につき取り直しが約 21 回 |
| ノートの画面で1行直す（広い画面、ノート N 冊） | 編集と確かめのそれぞれで N+8 本、合わせて 2N+16 本（3冊で 22 本）と、そのプリフライト | コードから数えた。実測はしていない |

原因（どれもコードで確かめた）：

- `Api.changes`（`app/lib/api.dart` の `_send`）は、GET 以外が成功するたびに増える。これを6か所が聞いていて、増えるたびに読み直す（入力ページ・サイドバー・`MeBuilder`・あとで確認・ノートを探す・資料の一覧）。
- 入力ページは最初の画面で、ほかの画面の下に残り続ける。その `_follow` は全ノートを取り直すので、どの画面で何を書いても（未整理メモを1件消しても）全ノートを取り直す。サイドバーは画面ごとに1つ作られ、下に隠れた画面のものも読み直す。
- 入力ページの読み込みは2段になっている。`GET /manuals` と `GET /shared` で ID を取り、そのあと1冊ずつ `GET /manuals/:id`（`input_screen.dart` の `_load`）。サーバーの `GET /manuals` も件数を出すために全ノートを読むので（`app.ts`）、同じノートを何度も読む。
- ノートを開くたびに、新しい `ManualController` が `GET /manuals/:id` を待ち、その間はスピナーになる（`manual_screen.dart`）。入力ページが同じ状態をもう持っていても使わない。
- API は Web と別のオリジンにあり、どの呼び出しにも `Authorization` が付くので、どの呼び出しにもプリフライトが付く。応答に `Access-Control-Max-Age` が無い（確かめた：本番の OPTIONS の応答。`hono/cors` は `maxAge` を渡さないと付けない）。ブラウザが覚えているのは短い間だけ（推測：既定は5秒。文書は読み直していない）。

### 1.4 Gemini を待つ所

時間は ADR 0002・0011・0012 の数字。本番には Gemini の使用量のログ（`gemini usage`）がまだ1件も無く（確かめた：直近10日で0件）、本番での分布は分からない。

| 操作 | 待つ相手 | いまの待たせ方 |
|---|---|---|
| 入力ページで記録する | assess（ふだん 5〜15 秒、遅いと約 20 秒） | `_busy` の間、入力欄ごと止まる。返るまで次を書けない（`input_screen.dart` の `_send`） |
| 記録のあとの書き込み | 差分1つにつき `apply`・`discard` を1本ずつ、順に | 終わるまで結果のカードが出ない（`review_dialog.dart` の `writeOrReview`） |
| 言われたことを直す | assess | ダイアログが止まる |
| ノートを作る（整える・ファイルから読む） | 約 5〜6 秒 | 待つ |
| 資料を足す | ページの数しだいで数十秒 | モーダルが止まる |
| ノートの行を直す | Gemini は待たない。保存の往復（サーバーで 0.13 秒＋通信）を待つ | 欄が閉じるまで待ち、次の行は「行を足す」を押し直す。確かめは裏で、1行ごとにノート全文つきの Gemini を1回（中央値 3.9 秒） |

メモ帳のように続けて書くと遅く感じるのは、行を直す所では「1行ごとに保存を待って、押し直す」こと、記録する所では「Gemini が返るまで次を書けない」ことから来ている。

### 1.5 画面の描き直し

- 入力欄に1文字打つたびに、画面全体を作り直している（`manual_screen.dart` の `_editor`、`input_screen.dart` の `_composer` と `_memoEditor`、`review_dialog.dart` の `onChanged: (_) => setState(() {})`）。
- ノートの画面は、全部の行を一度に作る（`SingleChildScrollView` と `Column`）。行ごとに `IntrinsicHeight` を使い、行ごとに全部の確認・差分・発言を先頭から探し（`models.dart` の `patch`・`utterance`・`openChecksFor`・`confirmationFor`）、マークダウンを読み直す。
- 1文字打ったときの描き直しを、Flutter のテストの中で測った（デバッグ実行なので本番の数字ではない。行数でどう増えるかを見る）。

| ノート | 1文字ぶんの中央値 |
|---|---|
| 12 行 | 7.9 ミリ秒 |
| 100 行 | 8.4 ミリ秒 |
| 450 行（直接編集 150 回） | 19.1 ミリ秒 |
| 900 行（直接編集 300 回） | 39.1 ミリ秒 |

今のノートの大きさでは問題にならない。数百行になると、1コマ（16.7 ミリ秒）に収まらなくなる。スマホではまだ測っていない。

## 3. 守ること

- AGENTS.md の実装の制約はそのまま：Gemini に状態を持たせない、JSON スキーマで受けて検証する、RAG にしない、呼び出しの回数と待ちの段数は減らす方向、土台の形を衝突検知の都合で変えない。
- **サーバーの裏で仕事をさせない**。Cloud Run は応答を返すと CPU を絞る設定なので（§1.2）、「先に返事をして、あとで Gemini を呼ぶ」は止まる。Gemini は、アプリが開いたままのリクエストの中で呼ぶ（直接編集の確かめと同じ形。ADR 0007）。キューの仕組みや常時の CPU は足さない。
- **判定の意味を変えない**。記録と確かめは、その時点のノートに照らす。2つを並べて走らせると、続けて書いた2つが互いに照らされない。Gemini を呼ぶものは1本ずつ、書いた順に送る。
- **古い応答で新しい状態を上書きしない**。発言と差分の ID はアプリが作って送る（今は `state.patches.last` で引いている）。送っていない変更が残っている間に届いた全状態は、そのまま差し替えない。
- **書いている行をずらさない**。行の編集欄は、行の番号（`_editing.at`）で場所を覚え、保存のときにその番号の行を読む（`manual_screen.dart` の `_save`）。欄を開いている間に取り直した状態が入ると、ほかの人の編集で行がずれ、別の行を書き換える。欄を開いている間は、そのノートの取り直しを画面に入れない（閉じてから入れる）。裏の取り直しを足す B1 と、欄を開いたまま次の行へ進む C1 で要る。
- プロンプト・モデル・考える量・1回にまとめる範囲を変える PR は、`eval/` の前後の数字を付け、ほかの PR と分ける。
- 状態管理のパッケージは入れない。アプリの状態を持つクラスを1つ足すだけにする。
- ボタンを足す・名前を変えるときは、先に `docs/spec/button-labels.md` に書く。

## 4. 直し方

### 4.1 読む：アプリが状態を1か所に持つ

- `app/lib/note_store.dart` に `ChangeNotifier` を1つ置き、自分（`Me`）・全ノートの状態（`ManualState`）・未整理メモを持たせる。画面はここから描く。
- 開いたときに `GET /home` を1本呼ぶ（新設）。自分・全ノートの状態・未整理メモをまとめて返す。サーバーは今ある `loadAll`・`getProfile`・`listMemos` を並べて読むだけ。ノートの並び順は今と同じにし、応答の並びで渡す。
- 書き込みの応答は、今も最新の `ManualState` を返している。それを store に入れれば、サイドバーの件数も入力ページの「あとで確認」も、取り直さずにそろう。`Api.changes` はやめる。
- ノートを開くときは、store にある状態をすぐ出し、裏で `GET /manuals/:id` を1本呼ぶ（ほかの人の編集を拾う）。アプリに戻ってきたとき（`AppLifecycleListener` の `onResume`。入力ページが今も未整理メモに使っている）に `GET /home` を呼ぶ。
- `GET /manuals`・`GET /shared` は、使う所が無くなったら消す。`ManualController` は store への薄い窓口にするか、無くす。
- 合わせて描き直しを軽くする：`ManualState` に ID からの索引を持たせる。入力欄の `onChanged` では、ボタンの押せる・押せないだけをその場で作り直す。発言の一覧は `ListView.builder` にする。ノートの行を必要な分だけ作るのは、「探した行まで送る」の作り直しが要るので、長いノートが出てきてからにする。

### 4.2 書く：ノートの行を直す

- 保存を押したら、アプリの中で行を書き換えて（`app/lib/history.dart` の `_apply` が、サーバーの `applyPatch` と同じ当て方をもう持っている）すぐ画面に出す。`POST /manuals/:id/edits` は裏で、ノートごとに1本ずつ順に送る。
- 発言と差分の ID はアプリが作って送る（`Edit` に ID を足す）。
- 失敗したら戻す。ほかの人が先に同じ行を直していた（409、ADR 0016）ときは、今ある選ぶダイアログを出す。通信の失敗は、画面を戻してエラーを出す。
- Enter で保存したら、すぐ下に次の行の欄を開く。メモ帳のように続けて書ける（§9 の 4）。
- 確かめ（Gemini）は今と同じく裏で呼ぶ。そのノートの編集を全部送り終えてから呼び、応答は「その確認1件」を手元の状態に足すだけにする（全状態を差し替えない）。
- 送り終える前にタブを閉じると、その編集は残らない。今は保存を待たせているので起きない。送信は 0.1〜0.2 秒で終わるので、まずは未送信がある間だけ画面に小さく出す。

### 4.3 書く：記録する

- 「ノートと照らし合わせる」を押したら、文面をすぐ未整理メモとして保存し（`POST /memos`、今ある）、入力欄を空ける。メモの付箋に「照らし合わせています…」と出す。
- 裏で `POST /utterances` を、今と同じく `memoIds` を付けて送る。記録できたらサーバーがメモを消すのも今と同じ。途中でタブを閉じても、文面は未整理メモに残る。
- 書き込みはサーバーで済ませる。今はアプリが差分ごとに `apply`・`discard` を1本ずつ順に送っている。同じ決まり（発言者が分かり、全部の差分に分類があれば、追記・補足は書き込み、同じ内容は書き込まず、矛盾は確認リストへ）を `POST /utterances` の中に移し、往復を 1+N 本から 1 本にする。
- 結果は、返ってきたときに今と同じ結果のカードで出す。発言者が分からないなど確かめが要るときは、書いている途中にダイアログを割り込ませず、カードの「確かめる」から開く（§9 の 3）。
- 関係するノートが無かったときは、メモを残して「記録先を選んでください」と出し、押すと今の選ぶダイアログを開く。
- ファイルを添えた記録は、未整理メモに文字しか入らないので、送り終えるまでファイルをアプリの中に持つ。タブを閉じると消える（今も、送っている途中で閉じれば消える）。
- 続けて記録したものは1本ずつ、書いた順に照らし合わせる（§3）。

### 4.4 Gemini の待ちそのもの

どれも判定に関わるので、1つずつ `eval/` の前後の数字を付ける。開いている PR #122 が同じ指示文を触っているので、順番を合わせる。

- まず本番の使用量のログを数日ためて、中央値・並べて送った割合・キャッシュの効きを見る（コードは変えない）。
- 直接編集の確かめ（分類だけ）の考える量を LOW にして比べる。整形と読み取りは LOW で 12〜27 秒が 5〜6 秒になった（ADR 0011・0012）。分類で同じだけ縮むかは推測。
- 続けて書いた行を、1回でまとめて確かめる。編集が止まって数秒たったら、まだ確かめていない行をまとめて渡す。10 行で 10 回が 1 回になる。プロンプトとスキーマが変わる。
- Gemini を呼ばなくても分かる編集では呼ばない：マークダウンの印や空白だけを変えた編集、食い違う相手（項目の行・確定の記録・資料）が1つも無いノートへの編集。
- assess の考える量を比べる。
- 記録先が「自動」だと、全ノートと全資料を毎回載せる。記録先の既定を変えるかは §9 の 7。
- 明示のキャッシュは、ADR 0019 の設計書 §9 の段階Bのまま（条件を満たしたら）。

### 4.5 最初の表示と、止まっていたサーバー

- 使っていないアイコンのフォント（1.8MB）を読ませない。`moon_design` が中で使っている `MoonIcons` の字があるかを先に調べ、使う字だけに絞ったフォントに差し替えるか、ビルドのあとに `FontManifest.json` から外す。
- `index.html` に、読み込み中の画面（方眼の地とアプリ名）を置く。
- `index.html` から、アプリ本体の読み込みと同時に API の `/health` を呼ぶ。止まっていたサーバーの起動（約 3.7 秒）を、本体の読み込みと重ねる。API の URL は、デプロイのときに `index.html` へ入れる。
- これが効くのは、ページを開いたときだけ。開いたままのタブに戻ってきたときは、B1 の「戻ってきたら取り直す」が起こす役になる（その取り直し自体は待たされるが、画面は持っている状態で出ている）。2日間の 28 回が、開いたときと戻ったときのどちらだったかは、ログからは分からない。
- Cloud Run の起動時の CPU の上乗せ（`startup_cpu_boost`。Terraform の google プロバイダーに項目があることは確かめた）を有効にする。
- 本番では起動時の `seedWithHistory` を呼ばない（メモリ保存のときだけ）。
- 最小 1 台にすれば起動待ちは無くなるが、毎月の費用がかかる（§9 の 2）。
- フォントの持ち方（§9 の 5）、`--wasm`、`Cache-Control` は、上を入れて測ってから決める。

### 4.6 サーバーの読み書き

温まったサーバーは速いので、体感への効きは小さい。ノートの履歴が増えたときのために、順番は後ろに置く。

- プリフライトを覚えさせる（`cors` の `maxAge`）。1行で入り、同じ URL への2回目からの往復が1本ずつ減る。回線の良い PC では1往復 0.02 秒ほどなので、効くのは回線の遅いスマホ（推測）。挙動を変えないので最初に入れる。
- 応答を圧縮する（`hono/compress`）。全部の経路にかかるミドルウェアで、音声入力の WebSocket（`/dictation`）も同じアプリが受けるので、そこを壊さないことをテストで確かめる。
- セッションをインスタンスの中で覚える（今は呼び出しのたびに Firestore を1回読む）。
- まとめて書く（Firestore の batch）。`propose` は差分が P 個なら 1+2P 回を3段で、`resolve` は最大 5 回、`edits` は 2 回を順に書いている。1回にすれば、途中で失敗して半端に残ることも無くなる。
- 書いたあとに全部を読み直さない。書いた内容を手元の状態に重ねて返す。
- 音声入力を始めるたび・切り出すたびに、認識の手がかりの語句のために全ノートを読んでいる（`phrasesOf(await loadAll(...))`）。利用者ごとにしばらく覚える。

## 5. 採らない案

- **Firebase Hosting の rewrite で API を同じオリジンにする**（プリフライトが全部消える）。Hosting を通すと 60 秒で打ち切られ、504 が返る（確かめた：Firebase の文書「Firebase Hosting is subject to a 60-second request timeout」）。Gemini の呼び出しは最長 114〜130 秒かかる（ADR 0002）ので通らない。
- **サーバーの裏で Gemini を回す**（Cloud Tasks、常時の CPU）。インフラと費用が増える。アプリから開いたままのリクエストで足りる（§3）。
- **応答を差分だけにする**。圧縮で足りるうちは、今の「最新の状態を丸ごと返す」を保つ。
- **埋め込みで Gemini を呼ぶかを決める**。この計画には入れていない。判定の取りこぼしに関わるので、別に評価してから考える。

## 8. 測り方

直す前と後で、同じ測り方をする。PR の説明に前後の数字を書く。

- 通信の本数：リリースビルド（`fvm flutter build web --release --dart-define=API_URL=...`）を手元の API（偽の Gemini・メモリ保存）につなぎ、Chrome の開発者ツールの Network で、ログイン直後・ノートを開く・1行直す・記録する、の本数を数える。
- サーバーの時間と止まっていた起動：Cloud Run のリクエストログを経路ごとにまとめる。`gcloud logging read 'resource.type="cloud_run_revision" AND httpRequest.requestMethod!=""'` で取り、URL のクエリ（音声入力のトークンが入る）は捨てる。起動の回数は `textPayload:"Starting new instance"` で数える。
- Gemini：`jsonPayload.message="gemini usage"` のログの `label`・`seconds`・`sent`・トークン数。
- 最初の表示：本番の各ファイルを `curl -H 'Accept-Encoding: br'` で取り、転送量を足す。
- 描き直し：行数を変えたノートで、1文字打つたびの `pump` の時間をテストで測る。実機では、プロファイルビルドを Chrome とスマホで開き、開発者ツールの Performance で見る（まだ測っていない）。
- 判定：`cd api && pnpm eval`。

## 9. 決めてほしいこと

1. **どこまで、どの順でやるか**。おすすめは、小さい A1〜A4 を先に入れ、そのあと、いちばん長く待たせている記録（C2）→ 行の編集（C1）→ 状態の持ち方（B1）→ B2。D は並べて進める。E は測ってから。本番（dev → main）に出すのを提出の前にするなら、1行で挙動の変わらない A1 だけにするのがよい。
2. **Cloud Run を最小 1 台にするか**。起動待ちは、開いたままのタブに戻ったときも含めて無くなるが、止まっている間も費用がかかる。金額は価格の文書を読めず、確かめていない（予算は月 3,000 円）。おすすめは、まず A2 の「先に起こす」と A3 を入れて測り、足りなければ金額を確かめて決める。
3. **記録を裏に回したとき、確かめが要る結果をどう出すか**。おすすめは、ダイアログを割り込ませず、結果のカードの「確かめる」から開く。
4. **Enter で保存して、すぐ次の行を書けるようにするか**。おすすめは、する（空のまま Enter か Esc で抜ける）。
5. **フォントを減らすか**。Bold を最初の画面のあとで読む（1.3MB 減。届くまで太字は Regular を太らせた字になる。推測）、第2水準の漢字を外す（足りない字は Noto Sans JP で補われ、書体がまざる）。おすすめは、A2 のあとで測ってから。
6. **Gemini の実験（D1〜D3）に eval の費用をかけてよいか**。
7. **記録先の既定を「自動」から変えるか**（最後に使ったノートにするなど）。自動は全ノートと全資料を毎回 Gemini に載せる。おすすめは、今のまま。ノートが増えて遅くなったら考える。

### 10.2 計画から変わった所

- **MoonIcons は外せなかった**。`MoonTextInput` が `errorText` を出すときに1字（U+ED49）を描く。外す代わりに、その1字だけに絞ったフォント（1,116 バイト）に差し替えた。アプリが絞ったフォントに無い字を描くようになったら、差し替えずに元のフォントを残す。
- **応答の圧縮は、小さい応答にもかかる**。`c.json` が `Content-Length` を付けず、`hono/compress` の下限が効かないため。害は無いのでそのままにした。
- **デプロイの順番**。新しいアプリは新しい API の口（`write`・編集の ID・`GET /home`）を使うので、`deploy.yml` の Web のジョブを API のあとにした。
- **結果のカードを複数並べる**。確かめが要る結果（誰が言ったか分からない・書き込めなかった行がある・関係するノートが無い）のカードは、次の結果が出ても消さない。関係するノートが無いときのボタン「記録先を選ぶ」を足した。あとから、確定していない食い違いのあるカードも、次の結果が出ても消さないことにした（続けて記録すると、食い違いを知らせたカードが流れて気づけなかったため）。
- **書き込みの前に読み直す**。assess の間にノートが変わることがあるので、サーバーは書き込む前にノートを読み直し、今の行に1件ずつ当てて確かめる。`appliedAt` は1件ずつ増やす。
- **アプリが作った ID が今ある ID と重なったら 409**。`store.put` は上書きなので、断らないと、共有された人がほかの人の記録を書き換えられる。
- **store の置き場は `Api`**（`api.store`）。画面のコンストラクターを変えず、テストの手直しを減らした。`GET /manuals`・`GET /shared`・`GET /me` はサーバーに残した（デプロイ直後の古いアプリが呼ぶ）。
- **D2 を2つに分けた**。Gemini を呼ばずに済む場合（食い違う相手が1つも無い・印や空白だけを変えた書き換え）は、プロンプトを変えないので先に入れた。続けて書いた行をまとめて確かめるほうは、eval が要るので未着手。
- **ADR の番号は 0021**。通知の ADR（#134）が 0020 を先に使ったので、この設計書と `docs/adr/0021-app-state-in-one-place.md` を 0021 にした。
- **読み込みは、当たらない差分で失敗しない**（#150）。書き込みが重なると、反映順に並べたときに当たらない差分が残り、ノートが開けなくなっていた。当たらない差分は飛ばし、未反映として返す。
- **照らし合わせの間にノートが変わっていたら、自動では書き込まない**。分類は assess が読んだ時点のノートに対するものなので、1行でも変わっていたら全部を未反映のまま残し、利用者が確かめる。
- **状態に読んだ時刻（`asOf`）を付ける**。応答の届く順は入れ替わるので、アプリは今持っている状態より古い `asOf` の状態を入れない。
- **確かめを省く条件を狭めた**。印や空白だけの書き換えで省くのは、前の行が直接編集で、その確かめの結果が残っているときだけ。
- **通知も `GET /home` で読む**。サイドバーの数は store から出し、通知のページは開いたら裏で1本読み直してから見たことにする。
- **ログアウトとログインで store を空にする**。セッションを覚える時間は5分から1分にした（ログアウトしても、もう1台のインスタンスでは覚えている間そのトークンが通るため）。

### 10.4 確かめていないこと

- **本物の Gemini と Firestore では動かしていない**。テストは偽の AI とメモリ保存だけ。「記録しても入力欄が止まらない」を確かめたのは、応答を遅らせた偽のサーバーの widget テスト。
- **ログインのあとの操作は、実際のブラウザで押せていない**（Chrome の自動操作でクリックが効かなかった）。ブラウザで確かめたのは、読み込み中の画面・起動時のフォント・`/health` の先起こし・ログイン直後の通信の本数だけ。
- 人の手で見る点：日本語の変換を決める Enter で次の行へ進んでしまわないか、Esc で欄が閉じるか、「誰が言った？」のエラーの i のアイコン、確かめが要る結果のカード、スマホの幅。
- 止まっていたサーバーの起動が実際にどれだけ縮んだか、プリフライトが本番でどれだけ減ったか。デプロイしてから §8 の測り方で測る。

### 10.5 分かっている制限

- 流し込んだ未整理メモで記録して失敗すると、元のメモと、まとめた文面のメモの両方が未整理メモに残る。
- 添付だけの記録で関係するノートが無く、そのカードを閉じると、読み取った文面は残らない。
- 届く前にタブを閉じた行の編集は残らない。ノートの画面を離れた直後に送信が失敗すると、知らせる場所が無い。応答が途中で切れたとき（サーバーには保存されたのに、アプリは失敗として戻す）に書き直すと、2回入る。
- 白紙のノートの1行目の確かめを省けるのは、2行目が届く前にその確かめが走ったときだけ。
- 書き込みの重なりそのものは防いでいない（当たらなくなった差分が未反映に戻る）。飛ばされたのが持ち主自身の直接の編集だと、記録の一覧に出ないので、編集をやり直すことになる。
- 確認ダイアログの「直して照らし合わせ直す」と行の確かめは、記録の列とは別に走る（前からの動き）。操作中の結果のカードが、裏で届いた次の結果で消えることがある。
- ログアウトのあとも、ノートの画面で積んでいた確かめの列は送り続ける。

### 10.6 コードレビューで直したもの

Opus のレビュアー4人（API とインフラ・入力ページ・ノートと状態・Web）と、統合の合わせ目を見る最終レビューにかけた。テストで再現して直したもの：

- 書き込みが重なるとノートが開けなくなり、`GET /home` が共有相手も含めて失敗する（#150）。
- 照らし合わせの間にノートが変わっても、古い分類のまま書き込む。同じノートを2回指定するとノートが壊れる。記録を保存したあとの失敗で記録全体が失敗になり、送り直すと二重に記録される。
- 関係するノートが無いカードと、未整理メモに戻った同じメモの両方から記録できて、2回入る。
- 確かめが要るカードが古い写しのまま扱われ、消える・古いまま残る。想定外の応答で待ちの列が止まり、何も出ない。
- 裏の読み直しが 404 だと、上に開いた確認リスト・履歴が落ちる。ほかの画面を開いている間に編集の送信が失敗すると、隠れた編集欄が開き直り、確認リストなどに変化が出なくなる。
- 応答の届く順が入れ替わると、古い状態で新しい状態が戻る。消したノートが、遅れて届いた応答で戻る。
- 印だけの書き換えで確かめを省く条件が広く、確かめの結果が残っていない行が二度と確かめられない。
- 読み込み中の画面を消したあとに一瞬白くなりうる。後処理が、消すはずのフォントが無いときにマニフェストだけ書き換えて止まる。
