# DiffNote（仮） 仕様

DevFest Hackathon 2026（教育テーマ）提出作のプロダクト仕様。検証結果に応じて更新する。変わらない前提と技術上の制約は `CLAUDE.md` にある。

## プロダクトの芯

**新人が、教わったことのうち文字になっていないことを覚え、矛盾した指示の板挟みから自分の身を守るための道具。**

- 対象の現場：マニュアルが更新されない職場（バイト中心の飲食店など）。上司がこまめにマニュアルを直す職場ではこの問題は起きないので、対象にしない。
- 職種は限らない。現場で体を動かしながら働く新人（飲食店など）だけでなく、PC の前で働く新人（エンジニアなど）も対象にする。例：コーディング規約に書いていないことを、「UUID を使うな」と言う先輩と、こだわらない先輩から別々に言われて挟まれる。
- 端末はスマホと PC の両方を本命として画面を作る。現場ではスマホで言われた直後に記録し、PC の前で働く人は Slack やレビューのコメントを PC で記録・確認する。PC では広い画面を使い、確認リストの一覧と詳細を並べる、サイドバーから直接移る、キーボードで送る、といった作りにする。
- 使う人：新人本人が、自分のために使う。入力の手間を払う人と得をする人が同じであることがこのプロダクトの前提。
- 既存の「暗黙知アプリ」や動画マニュアルは、組織や教える側が知識をまとめるための道具。このアプリは教わる側の道具で、立ち位置が逆。最初の明文化は既存の道具の仕事、明文化のあとに口頭で生まれ続ける差分を覚えるのがこのアプリの仕事。
- 扱うものは「ノート」と呼ぶ。職場のマニュアルはその一つにすぎず、自分用のメモやコーディング規約も同じように扱う。マニュアルという呼び名は、試すために差し込んだ使い方に寄りすぎているので画面では使わない（コード・API の `manual` は呼び替えていない）。
- ノートは、今あるマニュアルやメモを貼り付けて作っても、題名だけで白紙から作ってもよい。冊数に制限はない。
- ノートには、口頭で言われたことを記録して差分として積むだけでなく、エディタとして行を直接書き足し・書き換え・削除できる。直接書いた行も、ほかの行や確定済みの記録と論理的に食い違えば、口頭の指示と同じように衝突として確認リストに入れる（ADR 0007）。
- 以下の「マニュアル」は、このノートのことを指す。

### やらないこと

- 上司・店長が導入する前提の機能（管理画面、全員への配信など）は作らない
- どちらの指示が正しいかをアプリが決めない。決めるのは確認された人で、アプリは「誰に確認するか」までを返す
- 共有、前の版に戻す、PDF出力は優先度を下げる（組織側の機能のため）

## 構造：土台と強み

案は2層に分かれている。強みの層は、検証結果によって差し替える可能性がある。土台を変えずに差し替えられるように作ること。

- **土台**：口頭で言われたことを、誰が・いつ言ったか付きで記録し、マニュアルへの差分として積み上げる。直接の編集も、自分がいつ書いたか付きの差分として積む
- **強み**：衝突検知と、その後の流れ（下記）

衝突検知は土台の上に乗る独立したモジュールとして実装する。土台のデータ構造が衝突検知の都合に引っ張られないようにする。

## 体験の流れ

1. **取り込み**：新人が最初の画面（「リワインド」と「整理・入力」を1タップで切り替え）から、次のいずれかで「田中さんから塩は小さじ1/2でいいと言われた」と入力する。どのマニュアルに対する記録かは選ばなくてよい
   - **リワインドモード（常時待ち受けからの即時ストック）**：待ち受けをオンにしている間、端末は直前60秒の音声をメモリ上だけで保持し続ける。口頭で言われた直後に大きな切り出しボタンを押すと、話し終わりまで待って発話のかたまりだけを切り出し、裏で Cloud Speech-to-Text v2 で文字に起こして「未整理メモ」として端末内に時刻つきでためる。その場では確認画面を出さず、指導中も連続で何度でも押せる。あとで時間があるときに「整理・入力」で未整理メモを選び、発言者や言葉足らずを補ってから送信する
   - **テキスト入力（音声入力つき）・ファイル添付（PDF／画像）**：「整理・入力」のテキスト欄に直接書くか、音声入力で文字を起こして整え、必要に応じて PDF や画像を添えて送信する
2. **差分化**：ファイル（PDF／画像）が添えられていれば Gemini でテキストに変換した上で、Geminiが関係するマニュアル（複数にまたがる場合はそれぞれ）を判定し、現行マニュアルに対するパッチ候補に変換する。発言者と日時を必ず付ける（本文に発言者名が含まれない場合は、差分の確認画面で補う）
3. **分類**：パッチを次の4つに分類する
   - `same`（同じ内容）：マニュアルのどこかの行と、言い方が違うだけで同じ。本文は変えず、同じことを言った人をその行の裏付けとして残す（[#10](https://github.com/df-dev-kuma/diff-note/issues/10)）
   - `addition`（追記）：既存の記述に触れない。承認後そのまま反映
   - `qualification`（条件付きの補足）：既存の記述と両立する（例：「忙しい日は1/2」）。併記で反映
   - `contradiction`（矛盾）：既存の記述と両立しない。下の4へ
4. **衝突の提示**：「マニュアル：塩小さじ1 ／ 田中さん（11/3）：小さじ1/2」と並べて見せる
5. **確認の支援**：誰に確認すればいいかの候補と、そのまま使える聞き方の文面を出す
6. **確定の記録**：「11/7 店長に確認：1/2で統一」のように、誰がいつ決めたか付きで確定させる
7. **証拠として使う**：後で別の人に聞かれたとき、確認の記録を見せられる

デモの山場は4〜7。ここが一番「身を守る」が伝わる場面なので、デモはこの流れを最優先で磨く。

## 技術スタック

| 層 | 選定 |
|---|---|
| フロントエンド | Flutter（後輩のモックを継続） |
| バックエンド | TypeScript（Hono）on Cloud Run |
| データ | Firestore |
| LLM | Gemini（Vertex AI 経由） |
| 音声認識 | Cloud Speech-to-Text v2 |
| インフラ構成管理 | Terraform |
| CI/CD | GitHub Actions |
| 認証 | デモ版はなし（単一ユーザー固定）。API は合言葉だけで守る（ADR 0003）。後から足せる形にしておく |
| 入力（MVP） | 常時待ち受け（遡り録音）・テキスト（音声入力つき）・ファイル（PDF／画像） |

### Gemini を使う理由（ピッチにも使う）

衝突検知はRAGと相性が悪い。衝突の相手は、検索で取り出さなかった段落にいることが多く、top-kで切った時点で見逃す。マニュアル全文＋確定済みの記録＋新しい入力を一度に載せられる長いコンテキストが、この問題を解く前提条件になる。全文を毎回載せるコストはコンテキストキャッシュで抑える。

### LLM と状態の分担

- Gemini の仕事は**意味判断だけ**：パッチ化、分類、衝突相手の特定、聞き方の文面生成
- 状態（マニュアル本文、記録、確定履歴）はバックエンドが持つ。Gemini に状態を持たせない
- Gemini の出力は必ず構造化（JSON スキーマ指定）して受け取り、バックエンド側で検証してから保存する

## 評価（衝突検知）

- 評価セット：キッチンで働くメンバーへのインタビューで集めた実例に、分類の正解ラベルを付けたもの（目標20〜30件）。`eval/` に置く
- 実行：手動。プロンプトやモデルを変えたときに `eval/` のスクリプトを回す
- 指標は2つを**分けて**測る
  - 矛盾の取りこぼし率（`contradiction` を他に分類した割合）
  - 誤って聞きに来た率（`contradiction` でないものを `contradiction` にした割合）
- 聞かれすぎると誰も使わなくなるので、後者を軽視しない
- プロンプトを変えたら、変更前後の数字を PR に書く

## 前提が崩れたときの方針

インタビューの結果で前提（特に「板挟みはよく起きる」）が崩れた場合、変えるのは強みの層だけ。土台を変える提案は、「新人が言われたことを残したいと思っていない」と分かった場合に限る。
