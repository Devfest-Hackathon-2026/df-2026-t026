# 0006 振り分け・差分化・分類を Gemini 1回の呼び出しにまとめる

- 日付：2026-11-08
- 状態：採用（ADR 0002 の「呼び出しを2本に分ける」と、ADR 0005 の「前段で振り分けてからマニュアルごとに差分化と分類」を置き換える）
- 関連：#25

## 背景

- ADR 0002・0005 では、入力ページからの記録で「関係するマニュアルの振り分け（`route`）1 回 → マニュアルごとに差分化（`patchify`）1 回 → パッチの数だけ分類（`check`）」を呼んでいた。前の結果を待ってから次を呼ぶので待ちが3段になり、マニュアル全文もそれぞれに送っていた。
- Gemini は応答に 10 秒前後、混雑時は 30〜60 秒かかることがある。呼び出しの回数と待ちの段数を減らすよう求められた。

## 決定

- 振り分け・差分化・分類を **1 回の呼び出し**（`api/src/assess.ts`）にまとめる。対象のマニュアル（入力ページからは登録済みの全マニュアル、マニュアル画面や記録先を選んだときはそのマニュアル）を番号付きで全文渡し、1 回の応答で、発言者・日付と、パッチごとに対象のマニュアル・分類・衝突相手の行・同じ内容の行・確認先・聞き方を返させる。
- どのマニュアルにも当たらなければ何も保存せず、読み取った文面を返して記録先を選んでもらう（ADR 0005 と同じ）。記録先を選んだときは、パッチが無くても発言を残す。
- 指示文は分けて持つ。差分化の指示は土台（`api/src/foundation/patchify.ts` の `patchifySystem`）、分類の決め方は衝突検知（`api/src/conflict/check.ts` の `checkRules`）に置き、`assess.ts` が組み合わせる。
- 保存の形は変えない。パッチは `patches`、分類は `checks` に分けて保存する（ADR 0001）。衝突検知の都合で土台のデータ構造を変えない、という趣旨は保つ。
- ADR 0002 のほかの決定（毎回マニュアル全文を載せる、JSON スキーマで受けて検証する、行は番号で指す、確定の記録に Gemini を使わない）はそのまま。

## 評価

`gemini-3.8-flash`、`eval/` の 18 件、1 回ずつ（#25 のコメント）。

差分化と分類をまとめたとき（マニュアル 1 冊）

| 指標 | 2本に分ける | 1回にまとめる |
|---|---|---|
| 矛盾の取りこぼし率 | 0%（0/6） | 0%（0/6） |
| 誤って聞きに来た率 | 0%（0/12） | 0%（0/12） |
| 分類の正答率 | 83%（15/18） | 83%（15/18） |
| 判定が変わったケース | - | なし |
| Gemini の呼び出し回数 | 36 回 | 18 回 |
| 1 件あたりの時間（中央値） | 10.7 秒 | 10.3 秒 |

振り分けもまとめたとき（`eval/multi.mts --overlap`：正解のマニュアルに、話題が重なるマニュアル 2 冊をまぜる）

| 指標 | 振り分け → 差分化と分類 | 振り分けも1回 |
|---|---|---|
| 振り分けの正答率 | 89%（16/18） | 100%（18/18） |
| 矛盾の取りこぼし率 ／ 誤って聞きに来た率 | 0% ／ 0% | 0% ／ 0% |
| 分類の正答率 | 83%（15/18） | 83%（15/18） |
| Gemini の呼び出し回数 | 38 回 | 18 回 |
| 1 件あたりの時間（中央値） | 12.7 秒 | 7.9 秒 |

## 結果

- 呼び出し回数とマニュアル全文を送る回数が減り、費用が下がる。
- 待ちの段数が 1 段になる。マニュアル 1 冊・指示 1 つでは時間はほぼ同じ（時間の大半は Gemini が考えて答えを書く時間）だが、振り分けがある入力ページからの記録では中央値 12.7 → 7.9 秒に縮んだ。
- 応答の形が崩れたときは、差分化と分類をまとめて呼び直す（1 回）。分類だけ失敗しても差分化からやり直しになる。
- マニュアルが増えると 1 回のプロンプトが重くなる（それまでの振り分けも全文を送っていたので、増えるのは差分化と分類の指示ぶん）。
- ファイル（PDF／画像）の書き起こし（`transcribe`）は前段で別に呼ぶまま（ADR 0005）。
