# 0021 アプリの状態を1か所に持ち、書いたあとに取り直さない

- 日付：2026-11-10
- 状態：採用（設計書 0021 の B1。先に入った C1・C2 の決まりもここにまとめる）

## 背景

- `Api.changes` は GET 以外が成功するたびに増え、6か所（入力ページ・サイドバー・自分の名前・あとで確認・ノートを探す・資料の一覧）がそれを聞いて読み直していた。入力ページは最初の画面でほかの画面の下に残り続けるので、どの画面で何を書いても全ノートを取り直していた。本番の通信（プリフライトを除く）の 94% がこの取り直しだった（設計書 0021 §1.1）。
- 入力ページの読み込みは2段（`GET /manuals`・`GET /shared` で ID を取り、1冊ずつ `GET /manuals/:id`）で、ノートの数だけ増えた。
- ノートを開くたびに `GET /manuals/:id` を待ってスピナーになった。入力ページが同じ状態を持っていても使わなかった。

## 決定

1. **状態の置き場を1つにする**：`app/lib/note_store.dart` の `NoteStore`（`ChangeNotifier` を1つ）に、自分（`Me`）・全部のノートのサーバーの状態（`ManualState`。自分のノート → 共有されたノートで、サーバーの並びのまま）・未整理メモ・読み込みの失敗を持つ。状態管理のパッケージ・基底クラスは足さない。置き場は `Api` が持ち（`api.store`）、画面は今までどおり `api` だけを受け取る。
2. **開いたときは `GET /home` の1本**：自分・全部のノートの状態・未整理メモをまとめて返す。サーバーは今ある読み方（`load`・`getProfile`・`listMemos`）を並べて読むだけで、並びは `GET /manuals`（作った新しい順）→ `GET /shared`（共有された新しい順）と同じ。`GET /manuals`・`GET /shared` は、デプロイ直後に古いアプリが呼ぶので残す。
3. **書き込みの応答を store に入れる**：状態を返す呼び出し（行の編集・反映・反映しない・記録を直す・確定・ノートを作る・記録）は、`Api` が応答の状態を store に入れる。ノートを消したら外し、共有された人が自分を外したときも外す。外したノートは覚えておき、そのあとに届いた書き込みの応答では戻さない（外したあとに読み始めた読み込みが返したとき＝共有され直したときだけ、また入れる）。メモの足す・直す・消す（記録できたメモを含む）と名前・アイコンの保存も store に映す。これでサイドバーの件数・入力ページの「あとで確認」・一覧は取り直さずにそろう。直接書いた行の確かめの応答だけは、確かめた確認1件を今の状態に足す（応答の全体は確かめを始めたときに読んだものなので、入れるとその間に書いた行が消える。ADR 0007）。
4. **`Api.changes` をやめる**：聞いていた画面は store から描く。資料の一覧は store に持たず、資料を足したあとと、資料の中（そこで消せる）から戻ったときにだけ読み直す。使わなくなった `listManuals`・`listShared`・`listMemos`・`me`・`ManualSummary`・`SharedManual`・`MeBuilder` は消した。
5. **取り直すのは次のときだけ**
   - 入力ページを開いたとき・ログインできたとき・「もう一度読み込む」：`GET /home`
   - アプリ（タブ）に戻ってきたとき（入力ページの `AppLifecycleListener` の `onResume`）：`GET /home`
   - ノートを開いたとき：store にあればすぐ出し、裏で `GET /manuals/:id` を1本。無ければ今までどおり読み込み中を出して読む。消されていた・共有を外されていた（404）ら、store から外し、古い内容を出さずに「見つかりません」を出す。コントローラーの状態は消さず、同じコントローラーを使う上の画面（確認リスト・履歴・資料）は今の状態のまま出す（そこからの書き込みは 404 になる）。ノートの画面は、書いている欄を閉じてから「見つかりません」を出し、そのあと届かなかった編集の欄は開き直さない
   - ほかの画面から戻ったとき・書いたあとは取り直さない
6. **入力ページ以外をいきなり開いても動く**：サイドバー・ノート一覧・あとで確認・ノートを探す・名前とアイコンは、store がまだ1度も読めていなければ自分で `GET /home` を1回呼ぶ（読んでいる途中なら同じ読み込みを待つ）。読めなければ今と同じ扱い（サイドバーは並べないだけ、画面は「読み込めませんでした」と再読み込み）。1度読めたあとは、戻ってきたときの読み直しに失敗しても今の表示を残す。ログインが切れていたら（401）入力ページはログインの欄を出す。
7. **古い読み込みで新しい書き込みを戻さない**：読み込み（`GET /home`・`GET /manuals/:id`）の応答は、読み始めてから書き込みの応答を入れたノート（とメモ・自分）には入れない。書き込みの応答どうしも届く順が入れ替わる（行の編集の応答が、あとで送った確定の応答より後に届く。数秒かかる記録の応答が、その間の編集の応答より後に届く）ので、サーバーはノートの状態に読み始める前の時刻 `asOf`（ISO 8601）を付け、store は今持っている状態より古い `asOf` の状態を、読み込みでも書き込みの応答でも入れない。`asOf` の無い応答（デプロイ直後の古いサーバー）は今までどおり入れる。
8. **`ManualController` は store から読む**：応答はコントローラーへ直接は入れず、store を通す1本の道にする。コントローラーは状態を読むたびに store のそのノートの最新を取り込み、そこに、まだ応答に入っていない自分の編集（C1）を重ねて出す。画面はコントローラーを聞くと store も聞くので、ほかの画面での確定・裏の取り直し・戻ってきたときの取り直しも、同じノートを出している画面（入力ページの結果のカードも）に入る。store を聞くのは画面が聞いている間だけなので、閉じずに捨てたコントローラーが store に残らない。
9. **書いている行をずらさない**：行の編集欄は行の番号で場所を覚えている。欄を開いている間は、store から来た状態（自分の編集の応答も、裏の取り直しも）を画面の土台に入れず、欄を閉じてから入れる。送っていない編集が残っている間は、編集の応答と裏の取り直しを取っておく（C1 の止め方を取り直しにも広げた）。確定・反映など行の編集でない自分の書き込みの応答は、欄が閉じていれば編集を待たずに入れる（届いていない編集はその上に重ねて出る）。欄は、確認リスト・履歴・資料・ダイアログが上に開いたときに閉じるので、そこでの確定は止めずに入る。

先に入った決まり（細部は各 ADR の追記）：

- **先に画面へ出す**：行の編集は応答を待たずに出し（ADR 0007 の追記）、記録は文面をすぐ未整理メモに置いて入力欄を空ける（ADR 0015・0006 の追記）。
- **ID はアプリが作る**：直接の編集の発言と差分の ID はアプリが作って送り、先に出した編集と応答を取り違えない（ADR 0007 の追記）。
- **Gemini を呼ぶものは1本ずつ、書いた順に送る**：記録の照らし合わせも行の確かめも、並べて走らせない。続けて書いた2つが互いに照らされず、食い違いを取りこぼすため（ADR 0006・0007・0015 の追記）。
- **サーバーの裏で仕事をさせない**：Cloud Run は応答を返すと CPU を絞るので、Gemini はアプリが開いたままのリクエストの中で呼ぶ（設計書 0021 §3）。

## 理由

- 書き込みの応答は、もう最新の `ManualState` を返している。それを1か所に入れれば、取り直さなくても全部の画面がそろう。
- アプリを開いたときの通信がノートの数に比例しなくなる（テストで数えた本数は下の「結果」）。
- 状態の置き場が1つなら、取り直しの止め方（決定 7・9）を1か所に書ける。

## 採らなかった案

- **コントローラーが store を聞き続ける**：入力ページの確認リストやカードは、作ったコントローラーを確認リスト・履歴へ渡し、`pushReplacement` で入れ替えながら使う。持ち主が閉じる時機を決めにくく、閉じると使っている画面が古いままになる。画面が聞いている間だけ store を聞く形にした（決定 8）。
- **書いたあとに、そのノートだけ取り直す**：応答に最新の状態があるので、1本でも余分になる。

## 割り切っていること

- ほかの人の編集やほかの端末でためたメモは、開いたとき・戻ってきたとき・そのノートを開いたときに出る（今も、自分が何かを書くまでは見えなかった。ADR 0013・0016）。
- 読み込みの途中にメモを書いたら、その読み込みのメモは入れない。ほかの端末のメモは次の読み込みで出る。
- 未整理メモの書き直しに失敗したとき（ほかの端末で消した・記録したなど）は、知らせてから `GET /home` で読み直す（ADR 0015）。

## 結果

アプリのテストの偽のサーバーで数えた本数（広い画面。プリフライトは数えていない）。

| 場面 | 前（ノート3冊 / 10冊） | 後（3冊 / 10冊） |
|---|---|---|
| 入力ページを開く | GET 9 / 16 本 | `GET /home` 1 本 / 1 本 |
| サイドバーからノートを開く | GET 4 本、読み込み中を出す | `GET /manuals/:id` 1 本、すぐ出す |

| アプリに戻ってくる | `GET /memos` 1 本 | `GET /home` 1 本 |

## 追記（2026-11-10）：通知も store に持つ（ADR 0020）

- あとから dev に入った通知（ADR 0020）のサイドバーは、`changes` のたびに `GET /notices` を読み直していた。`changes` はやめたので、`GET /home` の応答に通知（`GET /notices` と同じ `{seenAt, items}`）を足し、store に持つ。`/home` はもう全部のノートを読んでいるので、同じ組み立てを使い回す。`GET /notices` は残す。
- サイドバーの新しい通知の数は store から出す。通知はほかの人の行いなので、自分が書いたあとには読み直さない。新しくなるのは、開いたとき・戻ってきたときの `GET /home`（決定 5）。
- 通知のページは、store の通知をすぐ出す（まだ読めていなければ読む）。開いた時点の見た時刻を控えて「新しい」を付けてから、見たことにする（`POST /notices/seen`）。見たことにできたら、Api が store の見た時刻を、今ある通知のいちばん新しい時刻まで進める（サーバーが付けた「今」はアプリに返らないため）。読み込みの途中に見たことにしても、その読み込みの通知は入れ、見た時刻だけ手元の新しい方を残す（見たことにしても通知そのものは古くならないので、決定 7 のように丸ごと捨てない）。
- 割り切り：通知のページを開いている間に届いた通知は、次に開くか戻ってくるまで出ない。store を読んだあとに届いた通知は、そのまま通知のページを開くと、サーバーが見た時刻を今にするので、次に読んだときに「新しい」が付かない。
