# 0001 マニュアルを「元の本文＋反映済みパッチ」として持つ

- 日付：2026-11-07
- 状態：採用

## 状況

文書の版管理（Firestore で自前管理するか、裏で本物の Git を使うか）はまだ決めていない（`docs/spec/spec.md`「未定事項」）。決まるまで、どちらかに依存する実装はしない。

## 決定

- マニュアルの正は、**登録時の本文（`base`）と、反映済みパッチの並び**とする。現行マニュアルは、パッチを反映順に `base` へ当てて毎回組み立てる。組み立てた各行には、その行を入れたパッチの ID が付く（`blame` 相当）。
- `base` は空でもよい。マニュアルが無い職場では白紙から始め、行なしの状態にパッチだけを積んで組み立てる。パッチには行を消す `delete` もある（2026-11-08 追記、ADR 0007）。
- パッチは「どの行を置き換えるか／どの行の後ろに入れるか」を、**行番号ではなく行の文字列**で指定する。作ってから反映するまでに別のパッチが入っても、対象の行が残っていれば当てられる。
- 口頭で言われたこと（`utterances`）とパッチ（`patches`）が土台。衝突検知の結果（`checks`：分類、衝突相手の行、確認先、確定の記録）は別のコレクションに持ち、パッチには分類を持たせない。
- 確認して確定したときは、その答えも「誰がいつ言ったか」付きの発言として土台に残し、マニュアルを変える場合はその発言からのパッチとして反映する。
- 保存先は `Store` インターフェースの裏に置く。

## 理由

- パッチ1件をコミット1件に写せるので、あとで Firestore 自前・Git のどちらに決めても、土台の形を変えずに保存先だけ差し替えられる。
- 行ごとに出どころ（誰がいつ言ったか、誰に確認したか）が引けるので、衝突検知が「主張単位」で既存の記述を参照できる。
- 衝突検知のデータを別に持つので、強みの層を差し替えても土台に手が入らない。

## 制約・既知の問題

- 同じ文字列の行が複数あると、最初の行に当たる。
- 表示のたびに全パッチを当て直す。デモ規模では問題ないが、パッチが数千件になったらスナップショットを持つことを検討する。

版管理を決めたら、このADRと spec の「未定事項」を更新する。
