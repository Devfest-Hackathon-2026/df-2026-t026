# 0012 ノートを作るときに、PDF・画像から本文を読み取る

- 日付：2026-11-09
- 状態：採用

## 背景

- 職場のマニュアルは、紙を撮った写真や PDF でしか手元に無いことが多い。「ノートを作る」画面は本文を貼り付けるか白紙から始めるかだけで、文字を打ち直す必要があった。
- 入力ページでは PDF・画像を添えて Gemini で書き起こしているが（ADR 0005）、それは「言われたこと」を起こすプロンプトで、ノートの本文を起こすものではない。

## 決定

1. 「ノートを作る」画面の本文の欄の下に「ファイルから読み取る」を置き、押したらすぐファイルを選ばせる。入力ページの＋のようにメニュー（「ファイルを選ぶ」「写真を撮る」）を挟むと一手間増えるため。本文の欄へのドロップと、本文の欄での貼り付けでも読み取る。形式は PDF・PNG・JPEG・WebP・HEIC、合わせて 10MB まで。
2. 選んだらすぐ Gemini を1回呼び（`POST /read`、`api/src/format.ts`）、書いてある通りに読み取って、「マークダウンに整える」（ADR 0011）と同じ書き方に整えた本文と、ノートの題名の案を返させる。前は整形を頼まず、整えたいときは「マークダウンに整える」を押していたが、待ちが2回になるので1回にまとめた（2026-11-09）。整形の決まりは `format.ts` の1か所に置き、どちらの呼び出しも同じものを使う。
3. 読み取った文で本文を置き換える。題名が空のときだけ、題名の案を入れる。作るまでは手で直せる。
4. ADR 0011 と同じく、ノートの状態には触れない別の呼び出しとし、ADR 0002・0006 の呼び出しの数には数えない。

## 理由

- 読み取りと整形を1回にまとめると、待ちが1段で済む。整形の決まりは1か所に置いたまま、両方の指示に入れるので、書き方はずれない。入力ページの書き起こし（ADR 0005）は、土台にテキストだけを渡すために前段で分けているが、ノートを作るときは土台を通らないので、まとめてよい。
- 整えた本文は作るまで手で直せる。読み取ったままの文が欲しいときは、元の資料を見て直す。
- 題名は1回の呼び出しに一緒に返させるので、呼び出しは増えない。
- まとめた呼び出しは、考える量を LOW にする。既定のままだと、まとめた分だけ考えて遅くなった。

## 評価

2026-11-09、`gemini-3.8-flash`。資料6種類（約40行のマニュアルの PDF、表の画像、ホワイトボードの写真、手書きふうのメモの写真、文字の PDF、スキャンした PDF）を2周、3通りを交互に呼んで比べた。並べて送る作り（ADR 0002）は3通りとも同じ。

| | 前（読み取り＋整形の2回） | まとめた1回・LOW |
|---|---|---|
| 1件の時間（中央値） | 20.0 秒 | 6.3 秒 |
| 1件の時間（平均） | 30.9 秒 | 11.6 秒 |
| いちばん遅い | 94.7 秒 | 31.9 秒 |
| Gemini に送った本数 | 33 本 | 17 本 |
| 数値・手順などが残った数 | すべて | すべて（40行のマニュアルは 20/20） |

- 見出しと箇条書きの形は、どちらもそろっていた。表は、行ごとの箇条書きか、品目ごとの入れ子のどちらかになった。
- まとめた1回でも、考える量が既定のままだと、別の時間帯に測って中央値 27.2 秒だった（LOW は同じ時間帯で 22.3 秒）。Gemini の混み具合で時間は大きく変わるので、比べるときは同じ時間帯に交互に呼ぶ。

## 制約・既知の問題

- 本文は置き換えるので、書いていた本文は消える。何枚かに分かれた資料は、一度にまとめて選ぶ。
- 本文の欄の外へのドロップと、欄の外での貼り付けは読み取らない。下の入力ページにも渡さない。
- 「写真を撮る」の項目は置かないので、カメラを直接は開けない。ファイルを選ぶ画面からカメラで撮れるかは、端末とブラウザによる。
