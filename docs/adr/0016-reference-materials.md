# 0016 ノートに資料（読むだけの原本）を置き、資料との食い違いも確認リストに出す

- 日付：2026-11-10
- 状態：採用（2026-11-10）
- 関連：ADR 0001・0002・0006・0007・0012・0013・0014・0016（共同編集）
- 設計書：[docs/design/0016-reference-materials.md](../design/0016-reference-materials.md)（データの形・API・プロンプト・画面・評価・実装の順番はこちら）

## 背景

- 利用者（はせさん）の言葉：「既存資料を Claude のプロジェクトみたいな感じでインポートして、そことの論理衝突も見れるようにしたい」。
- 店のマニュアル、社内の規約、授業の資料などは、新人が書き換えるものではなく、配られた原本として手元にある。口頭で言われたことや自分で書いたことが、ノートだけでなく資料の中の箇所と食い違っていても、今は気づけない。
- 今も PDF・画像からノートを作れる（ADR 0012）。ただしそれは資料をノートの本文に写す形で、写したあとは編集できるノートになり、出どころ（どの資料の何ページか）は残らない。1冊のノートに置けるのは、本文として写した1つだけ。
- 判定（assess・直接編集の確かめ）に載るのはノートの本文と確定の記録だけなので、ノートに写していない資料の箇所は相手にならない。

## 決定

1. **単位はノート**。資料はノートに付ける（ノート＝プロジェクト）。保存先はノートの下の新しいコレクション `materials`。資料を複数のノートで使い回すライブラリや、「プロジェクト」という新しい単位は作らない。
2. **資料は書き換えない原本**。取り込むときに1回だけ文字にし、以後は書き換えない。PDF・画像は ADR 0012 と同じ仕組み（Gemini、考える量 LOW）で読み取る。ページの区切りを保ち、行はページをまたいで通し番号にする。**原本のファイルは持たない**（Cloud Storage を使わず、infra に触らない）。書き起こした文だけを持つ。
3. **取り込める形と上限**：PDF 1つ（30ページまで）、画像 10枚まで、貼り付けた文のどれか。ファイルは合わせて 10MB まで（今の上限と同じ）。取り込むときにトークンを数え（countTokens）、1冊 3万トークン、1人（自分のノート全部）で合わせて 10万トークンまでにする。数字は案で、根拠と測り方は設計書の §5.6。
4. **判定は RAG にしない**。資料の全文を、ノート全文・確定の記録と一緒に毎回載せる。Gemini の呼び出しは増やさない（記録は assess 1回、直接編集の確かめは1回のまま。ADR 0006・0007）。資料の行は `M1 L23`（資料の番号と行番号）で指す。
5. **プロンプトの並び**は「指示 → 資料 → ノート → 確定の記録 → 発言者・基準日・メモ」にする。変わらない資料を前に置き、暗黙のコンテキストキャッシュに乗せる。資料に結び付いた確定は資料のブロックの中に書かず、後ろの「確定済みの記録」に `資料M1 L23` を添えて書く（確定のたびに資料のブロックが変わらないように）。明示のキャッシュ（cachedContents）は、暗黙のキャッシュを測ってから、条件を満たしたときだけ入れる（設計書 §9）。
6. **資料が0冊のノートでは、指示文・プロンプト・スキーマを今と1文字も変えない**。今の `eval/` 18件の数字と、資料を使わない人の挙動をそのまま守る。
7. **食い違いの相手の持ち方**：`Check` に `materialRef`（資料の ID・題名・ページ・行番号。ノートの行が相手なら null）を足す。`conflictLine`・`sameLine` は今まで通り「相手の行の文」のまま。資料の行も、矛盾の相手と同じ内容の相手の両方になれる。土台（`Manual`・`Utterance`・`Patch`）の形は変えない。
8. **#86 を繰り返さない**：資料は書き換えないので、指した資料の行が後で無くなることは無い。資料に結び付いた確定は、指せる資料の行と一緒に見せる。消した資料の確定は判定に見せない。Gemini に「相手にしてよい」と見せるものは、必ず番号で指せるようにする。
9. **何が正か**：資料は書き換えない。確定の記録は資料より優先する（プロンプトに書く）。確認の結果が「資料のまま」ならノートは変えない（直接書いた行は消す）。「新しい方」「別の内容」なら、決まった内容の行をノートに残す。表は設計書 §8。
10. **共有（ADR 0013・0016 共同編集）**：共有された人は資料の一覧と中身を見られる。足す・消すのは持ち主だけ。共同編集で、共有された人もノートを消す以外のことはすべてできるようになったが、資料を足す・消すはその例外にする（`mustOwn`）。共有された人の記録・直接編集も、持ち主の資料と照らし合わせる。
11. **消す（ADR 0014）**：ノートを消すと資料も消える（`FirestoreStore.removeManual` が消すコレクションに `materials` を足す）。資料を1冊ずつ消すこともでき、持ち主だけができる。
12. **資料どうしの食い違いは今回は見ない**。後の案にする。

## 理由

- ノートの下のコレクションにすれば、共有（ADR 0013）・消す（ADR 0014）・認可（`load`・`mustOwn`）をそのまま使える。`Store` の汎用の `list`・`put`・`remove` で読み書きでき、メソッドを足さずに済む。
- 資料を書き換えないので、資料の行を指した確認は、あとで相手の行が無くなることが無い。ノートの行を指す今の確認で起きた #83・#86 のような「指す相手が消えた」問題が、資料の側では起きない。
- 原本のファイルを持たなければ、Cloud Storage のバケット・権限・署名付き URL・消すときの連動が要らない。判定に使うのは書き起こした文で、出どころ（ページと行）はそこに付けられる。原本は利用者の手元にある。
- 全文を載せる理由は spec の「Gemini を使う理由」と同じ。衝突の相手は、検索で取り出さなかった段落にいることが多い。
- 呼び出しを分けず、1回の assess に資料を足すので、待ちの段数も呼び出しの回数も変わらない（ADR 0006）。資料ぶんの入力は増えるが、資料を前に置けば暗黙のキャッシュで抑えられる（Vertex AI の文書で、キャッシュした入力は 90% 引き。設計書 §12）。
- 資料が0冊のときにプロンプトを変えなければ、今の評価と利用者の挙動を守ったまま、資料つきのケースだけを測り直せばよい。

## 採らなかった案

- **今の ADR 0012 の形（資料をノートに写す）のまま使う**：出どころが残らず、1冊のノートに資料を何冊も置けない。写したあとは本人が書き換えられるので、原本との食い違いを見る用途に合わない。
- **資料のライブラリ（複数のノートで使い回す）・「プロジェクト」という新しい単位**：保存先・共有・消すときの連動・認可がすべて増える。今はノート＝プロジェクトで足りる。
- **RAG（資料を検索して関係する所だけ載せる）**：spec の理由で採らない。
- **資料用に判定の呼び出しを分ける**：呼び出しと待ちが増える（ADR 0006 の逆）。
- **原本のファイルを Cloud Storage に持つ**：infra と権限と消す処理が増える。読み取りの誤りを画面で照らし合わせられる利点はあるが、今は書き起こした文で足りる。後で要るなら足せる（`materials` の形は変えずにファイルの場所を足すだけ）。
- **資料の行を書き換えられる・読み取りを直せる**：原本でなくなり、資料の行を指した確認の相手が変わる（#86 と同じ問題が資料の側でも起きる）。直したいときは消して入れ直す。
- **資料に結び付いた確定を、資料の行の後ろの〔〕に書く**（ノートの行と同じ書き方）：確定のたびに資料のブロックが変わり、プロンプトの前方一致が切れてキャッシュが効かなくなる。
- **明示のキャッシュを最初から使う**：最小トークン数・保存の費用・作り直しの手間がある。暗黙のキャッシュで足りるかを先に測る。

## 割り切っていること

- 資料どうしの食い違いは見ない。
- 資料は「ノートを探す」の対象にしない。
- 読み取りの誤りは直せない。消して入れ直す。原本は持たないので、アプリの中で原本と見比べることはできない。
- 資料を消すと、その資料に結び付いた「資料のまま」の確定は、以後の判定に使わない（確認リストの記録には残る）。
- 表は行ごとの箇条書きになる（ADR 0012 と同じ）。

## 評価

- 資料が0冊の今の18件は、変更前と判定が同じであること。
- 資料つきのケースを足し、矛盾の取りこぼし率と誤って矛盾とした率を分けて測る。長い資料をまぜたときの誤検知も測る。件数・種類・出してよい基準は設計書 §11。

## 決めたこと（設計書 §15 の答え。2026-11-10）

1. 原本のファイルは持たない（書き起こした文だけ）。
2. 上限は1冊3万トークン・1人10万トークン、PDF は30ページまで。
3. 資料への入口は、ノートのページの上部バーの「資料」。
4. 共有された人は資料を見るだけ。
5. 資料と同じ内容は same（ノートに書き込まない）。
6. 「資料のまま」に決まった、直接書いた行は消す。
7. 資料を消しても「あとで確認」は残す（確定もできる）。
8. PDF の分割に `pdf-lib` を足す（MIT。最新は 1.17.1、2021-11-06 公開）。
9. 評価に使う長い資料は、チームで書いた架空のマニュアルにする。
10. 締め切りの前に、実装を PR4（確認で資料の箇所を見せる）まで進める。
11. 見本のノートに見本の資料は入れない（今は）。
12. 暗黙のキャッシュの durable は切らない。
