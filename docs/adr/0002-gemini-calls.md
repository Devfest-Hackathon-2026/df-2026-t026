# 0002 Gemini の呼び出しを2本に分け、毎回マニュアル全文を載せる

- 日付：2026-11-07
- 状態：一部を ADR 0006 で置き換え（振り分け・差分化・分類は1回の呼び出しにまとめた。全文を載せる・スキーマで検証するなどはそのまま）

## 決定

- Gemini の呼び出しは2本。
  - 土台の **差分化**（`api/src/foundation/patchify.ts`）：マニュアル全文と発言 → 発言者・日付・パッチ候補
  - 衝突検知の **判定**（`api/src/conflict/check.ts`）：マニュアル全文（行ごとの出どころ付き）・確定済みの記録・パッチ → 分類・衝突相手の行・同じ内容の行・確認先・聞き方
  - 音声（Cloud Speech-to-Text v2）・ファイル［PDF／画像］（Gemini）のテキスト化と、複数マニュアルからの対象判定は、この2本の前段で行う（ADR 0005）。
- どちらも RAG にせず、**毎回マニュアル全文**を行番号付きで載せる。衝突の相手は、パッチが触る行とは別の段落にいることが多いため。
- 応答は Zod で書いたスキーマを JSON スキーマに変えて `responseJsonSchema` に渡し、受け取ったあとも同じスキーマで検証する。行番号の範囲や「矛盾なら衝突相手と確認先が必須」もここで確かめ、形が合わなければ1回だけ呼び直す。
- Gemini は行を番号で指し、バックエンドが行の文字列に直して保存する（ADR 0001）。
- 確定の記録（確認の答えの反映）には Gemini を使わない。確認した人・日付・確定した内容は本人が選び、決まった通りに記録する。

## コンテキストキャッシュ

- プロンプトは、変わらない部分（指示・マニュアル全文・確定済みの記録）を前に、毎回変わる発言を後ろに置き、暗黙のキャッシュに乗りやすくしている。
- 明示的なキャッシュ（`caches.create`）はまだ使わない。モデルごとに最小トークン数があり、デモ規模のマニュアルはそれに届かない見込みのため。マニュアルが大きくなったら、下限を確かめてから入れる。

## 呼び出しのやり直し（2026-11-09 追記）

- 1本の上限は90秒で、遅い依頼も打ち切らずに待つ。20秒たっても返事がなければ、中身を変えた依頼を並べて送り、先に形の合った応答を使う（残りは止める）。合わせて3本まで（`api/src/gemini.ts` の `requestJson`）。1回の呼び出しは長くても130秒で終わり、書き起こしと assess の2回が Cloud Run のリクエスト上限（300秒）に収まる。
- 混雑・レート制限・時間切れ（408・429・500・502・503・504、応答が来ないまま打ち切ったもの）は、20秒を待たずに次の1本を送る（1秒・2秒あけて）。形が合わない応答は1回だけ呼び直す。
- 2本目からは、プロンプトの末尾に改行を足して前と同じ中身にしない（2本目は1つ、3本目は2つ）。1本目はそのまま送るので、`eval/` の結果と暗黙のキャッシュには影響しない。余分に呼ぶのは20秒を超えたときだけ。
- 前は SDK のやり直し（`retryOptions`）に任せ、1本40秒で打ち切って同じ中身を3回送っていた。`global` の Gemini は、中身がまったく同じ依頼をしばらく同じくらい遅く返すので、遅い中身に当たると3回とも時間切れになり、約2分待ってから失敗していた。PDF・画像の書き起こしでは、50回中24回がこれで失敗した。
- 中身ごとに遅さが決まっていることは、表の画像の書き起こしで、プロンプト末尾の改行の数だけを変えた5通りを2回ずつ送って確かめた。どの中身が遅いかは十数分で入れ替わることがあり、中身を変えるだけでは確実に速くならない。そのため、打ち切って送り直すのではなく、遅い1本を待ちながら並べて送る。

| 末尾の改行 | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 1回目 | 32.8 秒 | 4.1 秒 | 41.1 秒 | 4.1 秒 | 7.1 秒 |
| 2回目 | 35.0 秒 | 4.6 秒 | 35.1 秒 | 16.4 秒 | 11.0 秒 |

- 遅れは、Gemini が中身を読む前の段階で起きている。考える量を減らしても速くならず（thinking 0 トークンで 64 秒）、使えない設定を断る 400 が返るまでにも 55 秒かかった。temperature を変えても遅いままで、指示の後ろに空白を1つ足すと 5 秒で返った。`gemini-3.8-flash` はリージョンの窓口（`us-central1`・`asia-northeast1`）では使えない（404）ので、窓口は変えられない。
- 変えたあと、本番と同じ設定で確かめた。
  - PDF・画像7種類の書き起こしを2周：14回すべて成功。並べて送ったのは3回（表の画像25〜26秒、チャットのスクショ51秒）で、ほかは3〜6秒。
  - 書き起こしから振り分け・差分化・分類まで（`POST /utterances`）5件：すべて成功（20〜71秒）。
  - `eval/` 18件：変更前後で全指標が同じ（分類の正答率100%、矛盾の取りこぼし率・誤って聞きに来た率ともに0%）。判定が変わったケースは無い。1件あたりの中央値は9.1秒→8.7秒。
- 呼び出しごとに、並べて送るまでの時間（`hedgeMs`）と考える量（`thinkingLevel`）を変えられる。入力ページの PDF・画像の書き起こし（`intake.ts`）は、書き写すだけなので考える量を LOW にし、ふだん3〜7秒で返るので8秒で並べる。ノートを作るときの読み取り（ADR 0012）と整形（ADR 0011）も LOW にする。assess は既定のまま（考える量はモデルの既定、20秒で並べる）。整形は並べるまでの時間を既定の20秒のままにする。
  - 書き起こしを7種類×2周、前（既定・20秒）と後（LOW・8秒）を交互に呼んで比べた。平均 11.1 秒 → 7.0 秒、いちばん遅い 28.6 秒 → 11.5 秒、すぐ返ったときは 3.8〜4.5 秒 → 2.1〜2.7 秒。数値・人名などは前後とも14回すべて合っていた。並べて送った回数は 4 回 → 7 回に増え、中央値は 4.5 秒 → 8.4 秒になった（1本目が8秒を少し超えて並べ、約10秒で返ったものが多かった）。

## assess を並べて送るまでの時間（2026-11-10 追記）

assess（ADR 0006）は、並べて送るまでの時間を 20 秒から 12 秒にする（上の項目の「assess は20秒で並べる」を置き換える）。

- 遅い1本は、待っていても25秒を過ぎるまで返らないことが多い。並べた2本目はたいてい7〜9秒で返るので、遅い件の時間はおおよそ「並べるまでの時間＋8秒」になる。ふつうの1本は5〜15秒で返る。
- `eval/` 18件を、20秒・15秒・12秒で交互に2回ずつ回して比べた（`gemini-3.8-flash`、各36件）。分類の指標はどれも同じ（正答率100%、矛盾の取りこぼし率・誤って聞きに来た率ともに0%）。

| 並べるまで | 20秒 | 15秒 | 12秒 |
|---|---|---|---|
| 2本送ったケース（36件中） | 3件 | 7件 | 7件 |
| 並べて速くなった件の時間 | 26.1・28.5秒 | 22.6・23.5・19.2・20.8秒 | 20.3・19.2・20.7・19.5秒 |
| いちばん遅い件（1回目・2回目） | 28.5秒・14.2秒 | 23.5秒・20.8秒 | 21.1秒・19.6秒 |
| 費用の見積もり（1件あたり） | 約0.78〜0.81円 | 約0.78〜0.80円 | 約0.79〜0.81円 |

- 12秒と15秒で余分に送った本数は同じで、12秒のほうが遅い件が2〜3秒短い。12秒で並べた件の中には、1本目が12〜21秒でそのまま返り、2本目を止めたものもある（止めた本のトークンは分からないので費用の見積もりに含めていない）。
- 2本目を送り始めるのが24秒後なので、1回の呼び出しは長くても114秒で終わり、Cloud Run のリクエスト上限（300秒）に収まる。
- 遅い1本が出るのは混み具合しだいで、2回目の20秒のように1件も出ないこともある。件数が少ないので傾向として扱う。

## 直接編集の分類を並べて送るまでの時間（2026-11-10 追記）

直接編集の分類（`checkWithGemini`、ADR 0007）は、並べて送るまでの時間を 20 秒から 8 秒にする。

- 差分化をせず分類だけなので、assess より速い。`eval/` 18件の発言をそれぞれ1行の追記として、並べて送らずに（1本目が返るまで待って）呼んだところ、中央値 3.9 秒、いちばん遅くて 5.9 秒で、12 秒を超えたものは無かった（`gemini-3.8-flash`）。分類は18件すべて正解と同じだった。
- ふだん3〜7秒で返る書き起こし（`intake.ts`）と同じ8秒にする。遅い1本に当たったときは、20秒待つより12秒ほど早く返る見込み。この18件では遅い1本が出なかったので、縮む幅は assess の測定（並べた2本目は7〜9秒で返る）からの見込み。

## 判定の方針

- モックの分類プロンプトは「迷ったら矛盾」だったが、仕様の「聞かれすぎると誰も使わなくなる」と逆向きなので採らない。「両立する読み方が自然にできるなら矛盾にしない。ただし同じ状況で数値・手順・担当・場所が食い違えば矛盾」とした。
- この方針は `eval/` の2つの指標（矛盾の取りこぼし率・誤って聞きに来た率）を見て調整する。
